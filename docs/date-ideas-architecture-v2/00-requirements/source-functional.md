# Требования к разработке MVP

> **Куда сходить на свидание**

Документ задает поведение Telegram-бота подбора свиданий в Москве, сбор и модерацию каталога, модель данных, интеграционные границы и проверяемые критерии приемки. Сквозное тестирование и приемка выполняются совместно.

## Статус требований

Согласованная продуктовая основа лежит в отдельном документе TO DO.

Открытые развилки вынесены в Q1–Q8. P0 — обязательное для выпуска MVP после принятия спецификации; P1 — улучшение, не блокирующее выпуск. 

| **Термин**      | **Значение**                                                     |
|-----------------|------------------------------------------------------------------|
| Место           | Постоянный объект с адресом и режимом работы                     |
| Событие и сеанс | Событие — программа; сеанс — конкретный интервал ее проведения   |
| Кандидат        | Извлеченная запись до проверки и публикации                      |
| Карточка        | Представление опубликованного места или события пользователю     |
| Подбор          | Запрос с уточнениями, выдачей и альтернативами в одном контексте |
| Жесткое условие | Ограничение, которое нельзя нарушить без изменения пользователем |
| Предпочтение    | Фактор ранжирования, не исключающий другие варианты              |
| Исключение      | Постоянный запрет показа объекта пользователю                    |


# 1. Пользовательские сценарии

| **ID**                   | **Основной путь**                                                        | **Исключение или результат**                           |
|--------------------------|--------------------------------------------------------------------------|--------------------------------------------------------|
| UC-01. Новый запрос       | Пользователь пишет условия → бот извлекает параметры → выдает карточки   | Если данных достаточно, анкеты для заполнения нет                     |
| UC-02. Неясный запрос     | «Хочу необычное свидание» → бот уточняет значимый параметр → подбор      | Можно выбрать «Неважно»; нет бесконечных уточнений     |
| UC-03. Обратная связь     | Карточка → «Подходит» или «Не предлагать» → обновление состояния         | Дубликаты исключенного места тоже запрещены            |
| UC-04. Альтернативы       | «Другие варианты» → следующая неповторяющаяся выдача в тех же условиях   | Исчерпание каталога показано явно                      |
| UC-05. Возврат            | Новый диалог → использование сохраненных предпочтений → новые варианты   | Условия прошлого свидания не копируются как постоянные |
| UC-06. Нет результата     | Фильтрация дала 0 → объяснение → предложение изменить условие            | До согласия жесткое условие не ослаблять               |
| UC-07. Переход            | Карточка → сайт или бронирование → внешний ресурс                        | Бот не подтверждает успешное бронирование              |
| UC-08. Управление памятью | Просмотр предпочтений/исключений → исправление или снятие → новый подбор | Удаление данных доступно отдельным подтверждением      |
| UC-09. Модерация          | Импорт/ручной ввод → проверка → публикация → повторная проверка          | Неполная или спорная запись остается вне выдачи        |

## Пример достаточного запроса

«В субботу вечером до 5000 ₽ на двоих, в центре, хочется спокойно поговорить». Бот уточняет дату только при неоднозначности, ищет по известным условиям и не требует заполнить остальные поля. «Центр» должен сопоставляться с согласованным набором районов, а не с произвольной догадкой модели.

## Пример пустой выдачи

«Не нашел проверенных вариантов в этом районе до 3000 ₽ на двоих. Могу поискать в соседних районах или увеличить бюджет. Что изменить?» Кнопка меняет только выбранное условие. Если нет данных о цене, такой объект нельзя выдать как гарантированно укладывающийся в бюджет.

# 2. Диалог и условия запроса

## FR-01. Начало и ввод

Бот принимает свободный текст и готовые варианты. Старт кратко объясняет назначение и предлагает написать запрос. Не требует отдельной регистрации или полной анкеты.

Приемка: Достаточный первый запрос приводит к выдаче без дополнительных обязательных шагов.

## FR-02. Нормализация условий

Сохранять бюджет, единицу бюджета, дату/интервал, время, район/метро, интересы, формат и ограничения. У каждого значения есть происхождение: текущий запрос, профиль или подтвержденное уточнение.

Приемка: «2000 на человека» преобразуется в 4000 на пару; исходная единица сохраняется.

## FR-03. Минимальные уточнения

Спрашивать только о неоднозначности или пробеле, мешающем подобрать вариант. Неизвестный необязательный параметр не блокирует поиск. Один вопрос за раз; после двух уточнений предложить поиск по известным условиям.

Приемка: Не спрашивать повторно уже известное. Для выбора сеанса без даты уточнить дату или предложить постоянные места.

## FR-04. Приоритет и изменение условий

Явные условия текущего запроса приоритетнее мягких предпочтений профиля. Постоянные запреты действуют до явного снятия. Противоречивые жесткие условия уточняются.

Приемка: Новый бюджет не изменяет постоянные предпочтения без команды. Запрос конкретного запрещенного места предлагает снять исключение, но сам его не снимает.

## FR-05. Дата и время

Интерпретировать относительные даты по Московскому часовму поясу и моменту сообщения. Хранить абсолютный интервал. Прошедшую дату и неоднозначное «в пятницу» уточнять, если возможны разные трактовки.

Приемка: «Сегодня» после московской полуночи относится к новой дате; прошедший сеанс исключен, даже если событие многодневное.

Команды: /start, /new, /preferences, /excluded, /delete_data, /help. Это контракт назначения команд; точные подписи кнопок можно менять без изменения поведения. Новый подбор не удаляет профиль или постоянные исключения.

# 3. Отбор и достоверность

## FR-06. Фильтрация и ранжирование

Сначала отбирать опубликованные актуальные объекты Москвы, применять жесткие ограничения, исключения и расписание; затем ранжировать по интересам, удобству и разнообразию. Предложение: до 3 карточек, допустимы 1–2 при нехватке.

Приемка: Модель не может вернуть ID вне разрешенного набора.

## FR-07. Погода (TO DO)

Для погодозависимых вариантов получать прогноз на нужный интервал. Применять условие «только в помещении» как жесткое. Порог неблагоприятной погоды задается статично.

Приемка: пока не придумала TO DO

## FR-08. Пустая выдача

Различать отсутствие подходящих объектов, неизвестные обязательные данные, исчерпание непоказанных и технический сбой. Предлагать изменить конкретное условие; выполнять новое сравнение после согласия.

Приемка: Бюджет, дата, постоянные исключения и ограничения не ослабляются автоматически. Близкие варианты с отклонениями не маскируются под точные совпадения.

## FR-09. Факты только из каталога

Цены, адреса, даты, режим и URL брать из опубликованной версии; тексты причины рекомендации строить на проверенных тегах и условиях. LLM используется для понимания и ранжирования, но не как источник фактов.

Приемка: Измененная моделью цена/ссылка блокируется валидатором; используется шаблонная карточка. Неизвестное поле не заполняется предположением.

## Правила бюджета и расписания

Бюджет означает стоимость основной активности для двух взрослых без дороги и необязательных покупок. Для диапазона цен проверять верхнюю границу; цену «от» нельзя считать гарантией попадания в лимит. Стоимость с неопределенной верхней границей исключается при жестком бюджете. Средний чек помечается как оценка и не является гарантией.

Для сеанса проверять конкретный интервал и статус. Для постоянного места — часы работы и исключения в календаре. Если пользователь указал полную длительность, она должна помещаться в интервал работы. При неизвестном режиме не обещать доступность в заданное время. 

# 4. Карточки и персонализация

## FR-10. Состав карточки

Показывать название, тип, краткое описание, адрес/район, известную стоимость с единицей, дату/время события, причину соответствия, основную ссылку и отдельную букинг ссылку при наличии. Для неизвестных некритичных полей писать не передавать их.

Приемка: Основная ссылка есть всегда. Не отображать кнопку бронирования с пустым URL. Проверенное расписание не означает наличие билетов.

## FR-11. Ссылки и действие

Переход открывает внешний ресурс. Использовать проверенные URL с допустимой схемой; не формировать их моделью. 

Приемка: Не принимать произвольный редирект URL из запроса; не показывать «Забронировано» после клика.

## FR-19. Обратная связь и исключения

«Подходит» фиксирует положительный сигнал. «Не предлагать это место» создает постоянное исключение. «Другие варианты» лишь меняет текущую выдачу и не означает постоянный отказ.

Приемка: Исключение сохраняется после /new и перезапуска. Для места исключаются связанные события в нем; отказ от события исключает все его сеансы, но не весь адрес.

## FR-20. Память и управление

Хранить явные предпочтения, историю показов и исключения. Выводить список и давать изменить его. Наблюдаемые лайки влияют на ранжирование, но не создают жесткие запреты.

Приемка: Можно снять конкретное исключение. Удаление профиля требует подтверждения; сброс диалога не удаляет профиль. Данные другого пользователя недоступны.

## FR-21. Показы без повторов

В рамках подбора не повторять уже показанные канонические объекты. Между подборами ранее показанные, но не исключенные, допустимы; новизна используется как мягкий приоритет. Проверять исключения непосредственно перед отправкой.

Приемка: Повторный импорт и объединение дублей не обходят запрет. Уже отправленную карточку нельзя считать новой; нажатие на ее старую кнопку учитывает актуальный статус объекта.

# 5. Сбор и модерация каталога

## FR-12. Источники и импорт

Хранить реестр Telegram-источников, статус, контрольную точку, ошибки и время последнего успеха.

Приемка: Повторный запуск не создает вторую публикацию. Ошибка одного источника не блокирует остальные. TikTok, Instagram и сайты не обязательны в MVP.

## FR-13. Нормализация и дубли

Сохранять оригинал и извлеченные поля раздельно; объединять упоминания одного объекта. Нечеткое сходство предлагает дубль модератору; не сливает похожие события автоматически.

Приемка: У записи прослеживаются источники каждого значимого факта. Разные сеансы одного события не теряются при объединении.

## FR-14. Рабочее место модератора (TO DO)

Дать очередь, просмотр оригинала, редактирование, поиск дубля, причину отклонения, публикацию и снятие. Перед публикацией валидировать обязательные поля и проверку источника.

Приемка: Без прав публикация невозможна. Неполный адрес или неподтвержденная дата события блокируют публикацию.

## FR-15. Жизненный цикл

Статусы: candidate → in_review → published или rejected. Published → needs_review при существенном изменении/истечении проверки; published → archived при завершении/отмене. Needs_review → published только после проверки. Rejected может вернуться в in_review вручную.

Приемка: В выдачу попадает только published с действующей проверкой. Изменение источника не перезаписывает опубликованные факты незаметно.

## FR-16. Актуальность

У объекта и критичных полей есть verified_at и valid_until. Постоянные места проверять не реже 30 дней, события — не реже 24 часов перед показом; срок может быть короче по источнику. Истекшее исключать, а не продлевать автоматически.

Приемка: Фильтр выдачи соблюдает срок даже при задержке фоновой задачи. Завершенный сеанс не показывается; у события могут остаться будущие сеансы.

## FR-17. Аудит и исправления

Записывать автора, время, старые/новые значения и причину решения. Сохранять снимок опубликованной версии, использованной в выдаче. Снятие доступно немедленно.

Приемка: По жалобе можно найти карточку, ее версию и проверяющего; после снятия она не попадает в новые выдачи и кеш.

## DR-01 Обязательность

Для публикации нужны название, тип, Москва, проверенный адрес, основная ссылка, источник, статус, модератор и срок проверки. Для события дополнительно нужны место и хотя бы один будущий сеанс с определенным началом и концом. Неизвестные цена и режим допустимы, но ограничивают применимость в выдаче.

## DR-02–DR-04 Идентичность и версии

DR-02: canonical_id стабилен; при слиянии сохраняются aliases, исключения переносятся на итоговый объект.
DR-03: публикация и новая версия атомарны, параллельное редактирование защищено version-check.
DR-04: candidate и published-данные разделены; удаление источника ставит связанную запись на проверку, а не подтверждает ее автоматически.

## DR-05–DR-06 Отсутствие и доступ

DR-05: null, «бесплатно» и нулевая цена различаются; неизвестный статус билетов не равен «доступно».
DR-06: пользовательские сущности принадлежат одному user_id; редактору не нужен доступ к полным частным диалогам для работы с каталогом.

# 7. Компоненты и интеграционные контракты

Предлагаемая архитектура: Telegram-адаптер → управление диалогом → сервис подбора → каталог и профиль. Отдельный процесс: коннекторы → очередь кандидатов → модерация → опубликованный каталог. Аналитика получает события обоих процессов. На старте допустим модульный монолит с фоновыми задачами; Kafka и микросервисы не являются требованиями.

| **Граница** | **Вход и результат**                                                                | **Отказ**                                                                 |
|-------------|-------------------------------------------------------------------------------------|---------------------------------------------------------------------------|
| Telegram    | update_id, user/chat, text/callback → ответ и состояние обработки                   | Повтор update не повторяет действие; очередь отправки с лимитами          |
| LLM         | Запрос + минимальный контекст → структурированные intent/slots или ранжированные ID | Таймаут/невалидная схема → шаблон, уточнение или детерминированный подбор |
| Погода      | Координаты + интервал → прогноз, время обновления и горизонт                        | Нет данных → явная неопределенность; прогноз не выдумывается              |
| Источники   | Источник + checkpoint → сообщения и ревизии                                         | Ограниченные повторы, backoff, очередь ошибок, ручной перезапуск          |
| Каталог     | Условия + пользователь → разрешенные версии карточек                                | Отказ хранилища → сообщение о сбое; не выдавать непроверенный кеш         |

## FR-18 Доставка и повторные действия

Обработку update и feedback выполнять идемпотентно. Повторное нажатие «Не предлагать» не создает второе исключение. Callback содержит непрозрачный идентификатор, связанный с пользователем и карточкой. Проверять принадлежность и актуальность; устаревшая кнопка не меняет чужой подбор. Отправку считать успешной только после подтверждения API Telegram; это доставка, а не доказательство прочтения.

## Внутренние операции

Предложение контрактов: create_request возвращает request_id/state/normalized_conditions; clarify_request обновляет условия с version; recommend возвращает delivery_id, card snapshots и reason_codes; submit_feedback принимает event_id и action; publish_candidate принимает expected_version. Транспорт и точные схемы OpenAPI выбирает разработка в R0.

Состояния запроса: received → clarifying/retrieving → delivered/no_results/failed. После уточнения — retrieving; «Другие варианты» создает новую delivery в том же request_id. Изменение основного замысла — новый request_id. Причины результата: NO_MATCH, UNKNOWN_REQUIRED_DATA, EXHAUSTED, DEPENDENCY_FAILURE.

# 8. Нефункциональные требования

Измерять сервисное время отдельно от ожидания ответа пользователя и задержки чтения сообщения.

| **ID**               | **Требование**                                                                                  | **Проверка**                                                              |
|----------------------|-------------------------------------------------------------------------------------------------|---------------------------------------------------------------------------|
| NFR-01. Скорость      | p95 подтверждения обработки ≤2 с; p95 выдачи ≤10 с. Общий deadline запроса 20 с                 | Прогон 1000 запросов при 10 одновременных; ≥95% в целевом времени         |
| NFR-02. Доступность   | Цель 99% за месяц для собственного backend; внешние отказы считать отдельно                     | Мониторинг успешности пробного запроса и ошибок зависимостей              |
| NFR-03. Нагрузка      | Профиль пилота: 10 одновременных подборов, каталог 10 000 объектов; числа конфигурационные      | Проверить без потери update; при перегрузке очередь и понятное сообщение  |
| NFR-04. Данные        | Резервная копия ежедневно; цели RPO ≤24 ч, RTO ≤4 ч                                             | Восстановить каталог, профиль, исключения на тестовом окружении           |
| NFR-05. Доступ        | Разделение ролей; проверка пользователя на каждом действии; секреты вне кода и логов            | Негативные проверки чужих ID и прав модератора                            |
| NFR-06. Внешний текст | Текст источника/пользователя — данные, не команды для системы; LLM без прав публикации          | Prompt injection не меняет статус, URL и фильтры                          |
| NFR-07. Наблюдаемость | request_id, latency, ошибки зависимостей, возраст очереди, расходы, актуальность                | По одному request_id восстанавливается путь без раскрытия личного текста  |
| NFR-08. Хранение      | Предложение: сырые диалоги 30 дней, аналитика 90; профиль до удаления; резервные копии 30       | Проверить очистку и отсутствие восстановления удаленного профиля в работу |
| NFR-09. Стоимость     | Настраиваемые лимиты вызовов/токенов на запрос и дневной бюджет; без скрытого платного действия | При лимите — шаблонный подбор или явная недоступность                     |
| NFR-10. Удобство      | Ключевые действия доступны текстом и кнопками; смысл не зависит от фото/эмодзи                  | Сценарий проходит без изображений и точного знания команды                |

Конфиденциальность: не собирать сведения о партнере, ориентации и точную геолокацию без необходимости; район можно задать текстом. Не отправлять Telegram ID и полный архив переписки в LLM. Удаление активных пользовательских данных — предложенный срок до 24 часов; резервные копии истекают по политике, повторное восстановление учитывает журнал удалений.

# 9. Аналитика и эксплуатационные сценарии

| **Событие**                    | **Когда фиксируется**                     | **Поля сверх базовых**                      |
|--------------------------------|-------------------------------------------|---------------------------------------------|
| request_started                | Принят новый смысловой запрос             | is_returning, conditions_present            |
| clarification_asked / answered | Вопрос отправлен / ответ получен          | slot, clarification_index                   |
| recommendation_delivered       | API Telegram подтвердил отправку карточек | delivery_id, card_ids, count, versions      |
| recommendation_feedback        | Принято «Подходит»/«Не предлагать»        | delivery_id, card_id, action                |
| alternatives_requested         | Принята команда «Другие варианты»         | previous_delivery_id                        |
| outbound_clicked               | Сервер redirect обработал переход         | delivery_id, card_id, link_type             |
| no_results / request_failed    | Подбор завершен без выдачи / ошибкой      | reason_code, dependency?                    |
| candidate_reviewed / published | Завершена проверка / публикация           | candidate_id, duration, decision, source_id |
| card_reported / corrected      | Принята жалоба / исправлены данные        | card_id, version, error_kind                |

Базовые поля: event_id, occurred_at, request_id при наличии, псевдонимизированный user_id при наличии, schema_version, environment, is_test. Сырые сообщения и полные URL с персональными параметрами не включать. События повторной доставки дедуплицировать по event_id.
