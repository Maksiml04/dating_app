# v0.12 — стабилизация фоновых задач и безопасность

## Реализованные изменения

1. **Fencing token для Dialogue Worker.** При захвате `request_operation` генерируется UUID владельца. После LLM/поиска обработчик повторно блокирует строку в PostgreSQL и применяет результат только при совпадении `status=processing` и `claim_token`. Восстановление зависших операций сбрасывает старый токен. Это предотвращает запись результата от старой попытки, завершившейся после повторного захвата.
2. **Telegram Sender recovery.** `reserved` означает ещё не начатую отправку и может безопасно вернуться в `pending` после истечения резерва. `sending` означает, что HTTP-запрос мог уйти; после падения такой статус переводится в `ambiguous` и **не отправляется повторно автоматически**. Переход в `sending` записывается до обращения к Telegram. До него проверяется актуальность поколения диалога и публикации, включая её последнюю версию.
3. **Миграция `0009_worker_fencing.py`.** Новые поля `request_operation.claim_token`, `telegram_outbox.reservation_token`, `telegram_outbox.reserved_at`, индекс. Старые `sending` при обновлении становятся `ambiguous`, `reserved` — `pending`, `processing` — `queued`.
4. **Защита админ-интерфейса.** Проверка секретов `compare_digest`, опциональный PBKDF2-SHA256 для пароля администратора (`ADMIN_PASSWORD_HASH`), сохранена совместимость с `ADMIN_PASSWORD` для локальной разработки. CLI `python -m app.security` формирует хеш без передачи пароля в аргументах командной строки.
5. **Наблюдаемость.** `/health` проверяет жизнь процесса, `/ready` выполняет `SELECT 1` и отвечает 503 при недоступной БД, `/api/admin/diagnostics/queues` показывает агрегированные статусы операций/доставок и закрыт `X-Admin-Key`.
6. **Compose.** Выделен отдельный однократный сервис `migrate`; API и workers запускаются только после его завершения. Пароли БД и MinIO больше не имеют дефолтов в Compose. Включены restart policies и API healthcheck.
7. **Регрессионные тесты.** Токены владельца, сброс аренды, недопущение двойной доставки, проверка секретов и хеша.

## Что нужно проверить в реальном окружении

- Docker Compose и Alembic на PostgreSQL 16 с pgvector: в этой среде Docker/PostgreSQL и часть Python-зависимостей отсутствуют, поэтому интеграционный прогон не выполнялся. **При обновлении с v0.11 остановите старые sender/dialogue workers ДО миграции**, чтобы две версии обработчиков не работали параллельно.
- Реальные `429`, сетевые таймауты и callback Telegram; безопасность подключения Telethon.
- Стратегию обработки `ambiguous`: требуется операторское расследование через Telegram/логи, **автоматического повторного отправления быть не должно**.
- Security hardening публичного окружения: TLS/ingress, распределённые rate limits, секреты в secret manager, политики хранения ПДн, резервное копирование/восстановление и аудит сессий администратора.
- Полную FSM, ручной UX модерации и E2E; v0.12 не означает готовность к production.

## Запуск

```bash
cp .env.example .env
# Задайте POSTGRES_PASSWORD и тот же пароль в DATABASE_URL,
# ADMIN_API_KEY, TELEGRAM_WEBHOOK_SECRET, MINIO_ROOT_PASSWORD.
# По желанию создайте ADMIN_PASSWORD_HASH: python -m app.security

docker compose up --build -d
curl -f http://127.0.0.1:8000/ready
curl -H 'X-Admin-Key: <ключ>' http://127.0.0.1:8000/api/admin/diagnostics/queues
```

**Важно:** значения из `.env.example` являются шаблонами и должны быть заменены. Не открывайте приложение в интернет без HTTPS, защиты от перебора и конфигурации секретов.
